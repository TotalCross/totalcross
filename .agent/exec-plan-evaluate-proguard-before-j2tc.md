# Evaluate ProGuard before J2TC using build-generated TCZ evidence

Status: completed autonomous compiler-investment experiment.

This ExecPlan follows `.agent/PLANS.md` and `AGENTS.md`.

## Purpose / Big Picture

The completed TCIR/JIT/AOT architectural work proved that TotalCross bytecode can feed a verified backend/runtime IR and native execution backends. It also established that TCIR begins after Java-level information has already been lowered and therefore should not be stretched into a substitute for a future Java-aware whole-program optimization layer.

Before investing in such a layer, this plan must obtain direct evidence that Java-bytecode optimization before J2TC produces meaningful improvements in the TotalCross artifacts that actually ship.

The experiment uses ProGuard as an external optimization oracle.

It is not a production ProGuard integration and it does not assume that ProGuard will become part of TotalCross.

The central experiment is:

```text
baseline

runtime Java classes
        |
        v
runtime JAR
        |
        v
J2TC / tc.Deploy
        |
        v
TCZ


experiment

same runtime Java classes
        |
        v
runtime JAR
        |
        v
ProGuard
        |
        v
optimized Java JAR
        |
        v
same J2TC / tc.Deploy
        |
        v
TCZ
```

The primary evidence comes from the resulting TCZ artifacts, not from the size of ProGuard's output JAR alone.

At completion, this plan must answer:

1. Does optimization before J2TC materially change the TCZs produced by the build?
2. Which categories of Java-level optimization are responsible for those changes?
3. Does optimization benefit mainly from local method transformations or from whole-program knowledge?
4. Does shrinking/reachability matter more than optimization?
5. Does J2TC already erase or reproduce most of the transformations performed by ProGuard?
6. Based on the evidence, where should TotalCross invest next?

The final recommendation must choose or rank concrete future directions such as:

- Java-aware whole-program HIR and optimizer;
- ProGuard as a short- or medium-term build pre-pass;
- reachability/tree-shaking infrastructure;
- targeted optimizations inside or immediately before J2TC;
- TotalCross-bytecode-specific optimization;
- continued TCIR/JIT/AOT investment; or
- obtaining a larger real-application corpus before making a major compiler investment.

No HIR, production ProGuard integration, or TCIR semantic expansion is implemented by this plan.

## Current Architecture and Scope

### Existing build corpus

`TotalCrossSDK/build.gradle` already creates four Java runtime archives:

```text
tc.base.lang.jar
tc.base.util.jar
tc.base.misc.jar
tcui.jar
```

and runs each through `tc.Deploy`, producing:

```text
tc.base.lang.tcz
tc.base.util.tcz
tc.base.misc.tcz
TCUI.tcz
```

These four artifacts are the primary corpus for this experiment.

They are preferable to an arbitrary sample application because they are:

- owned by this repository;
- produced from the exact revision being investigated;
- reproducible by the ordinary SDK build;
- significant inputs to real TotalCross deployments;
- independent of external private applications; and
- sufficiently different in purpose to reduce the risk of drawing conclusions from one code shape.

The experiment must always preserve results per TCZ as well as aggregate totals.

A large aggregate improvement caused entirely by one artifact must be reported as such rather than generalized to all TotalCross code.

### Existing conversion path

The production path is:

```text
Java classes
    |
    v
JAR
    |
    v
tc.Deploy
    |
    v
J2TC
    |
    v
TCClass / TCMethod / TCCode
    |
    v
TCZ
```

The experimental path must use this same converter and deployer.

Do not create a special Java-to-TC converter for the experiment.

`tc.Deploy` supports a target directory through `/o`; use it to place experimental TCZ files under the experiment build directory instead of overwriting ordinary `build/libs`, `dist/vm`, or installation artifacts.

### TCZ as the evidence boundary

A TCZ contains named compressed chunks and records both compressed and uncompressed chunk sizes.

Use the final TCZs as the primary measurement boundary.

For every TCZ record at least:

```text
artifact name
variant
input revision
input JAR SHA-256
optimized JAR SHA-256
TCZ SHA-256

final TCZ bytes
chunk count

compressed bytes per chunk
uncompressed bytes per chunk

total compressed chunk bytes
total uncompressed chunk bytes

ConstantPool compressed bytes
ConstantPool uncompressed bytes

per-class/chunk compressed bytes
per-class/chunk uncompressed bytes

classes/chunks added
classes/chunks removed

compression ratio
```

Report the largest positive and negative per-entry deltas.

Compressed TCZ bytes alone are not enough to infer compiler benefit because compression may amplify or hide structural changes.

Prefer uncompressed class payload and TotalCross-code structural metrics when explaining why a variant changed.

### Optional converter structural evidence

If TCZ size differences are meaningful but insufficient to explain the transformation, add a small experiment-only metrics hook at the J2TC boundary.

It may collect, where available without changing serialized output:

```text
class count
method count
total TCCode slot count

CALL_normal count
CALL_virtual count

NEWOBJ count
array allocation count

branch count

field load/store count

CHECKCAST / INSTANCEOF count

total iCount
total oCount
total v64Count
```

The hook must be opt-in and have no effect on normal converter output.

Prefer analyzing existing `TCClass`, `TCMethod`, and `TCCode` structures over introducing production compiler APIs.

If the documented TC class format makes the same metrics inexpensive to recover from final TCZ entries, prefer post-build artifact analysis.

Do not implement a general TCZ/TClass disassembler merely for this experiment unless the evidence proves it necessary.

## Plan of Work

### Milestone 1: establish the exact baseline

Produce the four normal runtime JARs and their four normal TCZs from the current revision.

Do not begin ProGuard comparison until the ordinary build baseline is reproducible.

Copy or reference immutable baseline artifacts under:

```text
build/proguard-tcz-experiment/<revision>/baseline/
```

without modifying the originals.

Run the TCZ analyzer and produce:

```text
baseline.json
baseline.md
```

Record SHA-256 values so all later comparisons can prove that they use the same starting revision and inputs.

Acceptance:

- all four normal runtime JARs exist;
- all four normal TCZs exist;
- the experiment analyzer can enumerate their chunks;
- reported file and chunk sizes agree with the actual artifacts;
- re-running analysis without rebuilding produces identical machine-readable results;
- normal build output remains unchanged by experiment tooling.

A baseline build failure is a hard experiment failure.

### Milestone 2: conservative module-local optimization

Process each runtime JAR independently through ProGuard.

Use:

```text
-dontshrink
-dontobfuscate
```

and one optimization pass.

Do not use aggressive optimization.

Each runtime JAR is program input only for its own run.

Use the other runtime JARs and required JDK/runtime dependencies as library inputs where necessary so ProGuard has type information without rewriting unrelated modules.

Conceptually:

```text
tc.base.lang.jar
      |
      v
ProGuard
      |
      v
tc.base.lang.optimized.jar
      |
      v
tc.Deploy
      |
      v
tc.base.lang.tcz
```

Repeat independently for all four modules.

Use exactly the same `tc.Deploy` and J2TC code as the baseline.

Place resulting TCZs under a variant-specific `/o` directory.

Capture:

- ProGuard success/failure;
- warnings;
- input/output JAR sizes as secondary evidence;
- final TCZ evidence;
- structural TC metrics if available.

A ProGuard or J2TC incompatibility for one module is not automatically a failure of the entire experiment.

Record that variant/module as rejected with its first stable diagnostic and continue with independently executable variants.

Acceptance is a complete per-module comparison between baseline and conservative module-local optimization.

### Milestone 3: measure whole-runtime optimization value

The previous milestone answers:

> How much can ProGuard improve each runtime module with only module-local program knowledge?

This milestone asks:

> How much additional opportunity appears when the optimizer can reason across the runtime modules?

Provide the classes from all four runtime JARs to a single optimization universe while still disabling shrinking, obfuscation, and aggressive optimization.

Because the normal build expects four JARs and four TCZs, preserve original class ownership.

Since obfuscation and shrinking are disabled, classes should retain stable names.

After optimization:

1. assign each output class back to the runtime JAR that owned that class in the baseline;
2. preserve required non-class resources from the corresponding baseline JAR;
3. fail the reconstruction if ownership is ambiguous or a class unexpectedly cannot be assigned deterministically;
4. rebuild the same four logical optimized JARs;
5. pass those JARs through the normal `tc.Deploy`/J2TC path.

Run at least:

```text
whole-opt-1 = one optimization pass
whole-opt-3 = up to three optimization passes
```

The multi-pass variant is evidence about iterative optimization opportunity, not the production recommendation by itself.

Compare:

```text
baseline
vs module-opt
vs whole-opt-1
vs whole-opt-3
```

Acceptance is evidence answering whether cross-module program knowledge materially improves the final TCZs beyond independent optimization.

### Milestone 4: attribute the optimization opportunity

Do not conclude merely that "ProGuard helped."

Identify which kinds of transformation account for the observed TCZ or TC-code changes.

Use ProGuard optimization filters to create controlled ablation variants.

At minimum consider these groups:

#### Local code/data-flow transformations

```text
code/simplification/*
code/removal/*
code/merging
code/allocation/variable
```

#### Interprocedural method transformations

```text
method/marking/*
method/removal/parameter
method/generalization/*
method/specialization/*
method/propagation/*
method/inlining/*
```

#### Field transformations

```text
field/removal/*
field/marking/*
field/generalization/*
field/specialization/*
field/propagation/*
```

#### Enum unboxing

```text
class/unboxing/enum
```

Do not automatically run every possible combinatorial subset.

Use an adaptive procedure:

1. compare full conservative optimization against baseline;
2. if the full variant produces only weak or negligible TCZ/TC-code changes, do not spend time running a large ablation matrix;
3. if the full variant produces meaningful changes, run grouped variants sufficient to identify the dominant categories;
4. split a group further only when its contribution is both material and relevant to a future TotalCross implementation decision.

For each group compare not only total TCZ bytes but also explanatory signals such as:

```text
TC code slots
call sites
virtual call sites
allocations
method count
register homes
class payload
constant pool
```

The result must distinguish, for example:

```text
"whole-program optimization helped"
```

from:

```text
"most of the gain came specifically from method propagation and inlining"
```

because these imply different TotalCross investments.

### Milestone 5: estimate shrinking/reachability opportunity

Only after optimize-only results are stable, evaluate shrinking separately.

This experiment must not confuse optimization with API removal.

Create a conservative library-safe shrinking configuration that preserves at least:

- externally visible public/protected SDK API required by the module boundary;
- native methods and their descriptor classes;
- TotalCross VM/runtime entry points;
- known runtime callback conventions;
- TotalCross `4D` replacement classes and required members;
- classes or members whose identity is required by deployment conventions;
- relevant reflection/Class.forName roots discovered by repository analysis;
- serialization-sensitive members when applicable; and
- any additional repository-proven dynamic entry points.

Do not obfuscate.

Run:

```text
optimize + conservative shrink
```

over the widest safe runtime view established by previous milestones.

Use existing API compatibility tooling or an equivalent baseline-versus-variant API snapshot to ensure the intended public/protected API surface remains present.

Produce ProGuard usage/seeds evidence when useful, but do not paste complete usage listings into the ExecPlan.

Treat this result as an estimate of the opportunity available from reachability/tree shaking.

It is not authorization to ship a shrunk SDK.

Acceptance:

- removed classes/members are measured;
- intended external API is preserved according to the experiment rule;
- resulting JARs still pass through J2TC;
- TCZ deltas are measured;
- dynamic/reflection/native limitations are explicit.

If safe keep rules cannot be established with reasonable evidence, stop this milestone and record shrinking as unresolved rather than weakening the rules until the build happens to work.

## Evidence Interpretation Rules

Use these ranges as heuristics for autonomous triage, not as product-performance claims.

### Strong structural signal

Approximately either:

```text
>= 10% reduction in aggregate TC code slots
```

or:

```text
>= 15% reduction in aggregate uncompressed TC class payload
```

with evidence not attributable solely to an irrelevant or pathological single artifact.

### Moderate structural signal

Approximately:

```text
3-10% TC code-slot reduction
```

or:

```text
5-15% uncompressed TC class-payload reduction
```

### Weak structural signal

Approximately:

```text
< 3% TC code-slot reduction
and
< 5% uncompressed TC class-payload reduction
```

These thresholds classify whether further compiler investigation is justified.

They do not estimate runtime speed.

A targeted transformation may still be important below these thresholds when it significantly reduces an expensive semantic operation such as:

```text
CALL_virtual
object allocation
boxing
```

Record those separately.

## Investment Decision Rules

The experiment must conclude with an evidence-based recommendation.

Apply the following decision logic.

### Whole-program HIR is strongly indicated

Prefer investment in a Java-aware whole-program optimizer/HIR when:

```text
whole-runtime optimization materially beats baseline
and
whole-runtime optimization materially beats module-local optimization
```

especially when the attribution comes from:

```text
method propagation
type specialization
devirtualization-enabling marking
inlining
enum unboxing
cross-method field propagation
```

The recommendation should identify the minimum high-level analyses actually supported by the evidence, for example:

```text
class hierarchy
call graph
argument propagation
devirtualization
inlining
```

Do not recommend building a complete R8 clone merely because some whole-program optimization helps.

### Local/pre-J2TC optimization is indicated

Prefer targeted optimizer work closer to the existing converter when:

```text
module-local ~= whole-runtime
```

and local code/data-flow transformations explain most of the TCZ change.

Candidates may include:

```text
constant propagation
branch simplification
DCE
copy propagation
local CSE
peephole optimization
```

The conclusion should state why a whole-program HIR is not yet justified by the measured corpus.

### Interprocedural HIR features are indicated

If method-level interprocedural transformations account for a large fraction of the gain, prioritize specifically:

```text
call graph
type propagation
argument propagation
return propagation
devirtualization
selective inlining
```

rather than beginning with unrelated HIR features.

### Enum optimization is indicated

If enum unboxing independently causes meaningful TCZ/code/allocation reduction, identify enum unboxing as a bounded high-return candidate.

The report should compare implementing this transformation internally versus retaining ProGuard as a pre-pass.

### Reachability/tree shaking is indicated

If conservative optimize-only variants are weak but library-safe shrinking substantially reduces TCZ payload/class/method count, prioritize:

```text
reachability
tree shaking
keep/pinning model
```

over a broad optimization framework.

### ProGuard itself may be a useful intermediate solution

If ProGuard produces substantial repeatable TCZ improvements, remains J2TC-compatible, and the required rules are manageable, recommend evaluating ProGuard as a separate short-term build pre-pass.

This recommendation must remain distinct from deciding whether a native TotalCross HIR is the long-term architecture.

Consider maintenance, licensing, debugging, reproducibility, keep-rule ownership, diagnostics, and compatibility before recommending production integration.

Do not implement production integration in this plan.

### Java-level optimization appears to have low leverage

If ProGuard substantially changes Java JARs but final TCZ structure changes only slightly, record that J2TC is already normalizing away much of the difference or that the TC representation prevents the transformations from surviving.

In that case prioritize investigation of:

```text
J2TC/TC bytecode optimization
TCIR optimization
JIT/AOT
runtime dispatch/allocation costs
```

according to the measured structural evidence.

### Evidence favors TCIR/JIT/AOT

If all conservative ProGuard variants produce weak TCZ/TC-code changes and shrinking is also small, this repository-owned corpus does not support a major HIR investment.

Update the TCIR continuation decision gate accordingly.

Do not claim that Java-level optimization is globally useless. State that the autonomous SDK corpus failed to demonstrate sufficient leverage and identify whether a real application corpus is the next necessary evidence.

### Compatibility failures are evidence

If specific ProGuard optimization families create bytecode that J2TC rejects or mis-converts, isolate the responsible family.

Record:

```text
input pattern
ProGuard family
resulting J2TC failure
whether ordinary javac can produce equivalent bytecode
estimated cost of supporting it
```

Then decide whether:

- J2TC should gain support;
- the transformation should be disabled;
- or an internal optimizer would avoid the incompatibility.

Do not simply add broad ProGuard exclusions until every test passes.

  Rationale: they are autonomous, repository-owned, reproducible, product-relevant artifacts produced by the existing SDK build.
  Date: 2026-08-08.

- Decision: Measure final TCZs rather than judging ProGuard from optimized JAR size.
  Rationale: the investment question is whether Java-level transformations survive J2TC and improve TotalCross artifacts.
  Date: 2026-08-08.

- Decision: Keep ordinary SDK build behavior unchanged.
  Rationale: this is an experiment, not a production integration.
  Date: 2026-08-08.

- Decision: Use conservative optimize-only variants before shrinking or aggressive optimization.
  Rationale: optimization, reachability, and semantics-relaxing transformations answer different architectural questions and must not be conflated.
  Date: 2026-08-08.

- Decision: Compare module-local and whole-runtime optimization.
  Rationale: the difference directly measures whether whole-program context is valuable enough to justify a richer Java-level optimizer architecture.
  Date: 2026-08-08.

- Decision: Attribute material gains by optimization family.
  Rationale: future TotalCross investment should reproduce only capabilities supported by evidence, not imitate ProGuard or R8 wholesale.
  Date: 2026-08-08.

- Decision: Treat individual optimization/conversion failures as experiment evidence when the baseline remains valid.
  Rationale: autonomous execution should continue far enough to identify which transformations are compatible and valuable rather than aborting on the first rejected variant.
  Date: 2026-08-08.

- Decision: Use pinned auxiliary SDK classes as program inputs but exclude them from measured outputs.
  Rationale: launcher, simulator, and excluded SDK classes depend on runtime program classes, which ProGuard cannot model safely as libraries. Pinning their exact classes preserves hierarchy/type facts without optimizing them or adding them to the four runtime JARs and TCZs.
  Date: 2026-08-08.

- Decision: Compare compatibility-adjusted variants to a separate baseline with only `LineNumberTable` removed.
  Rationale: optimized line tables whose first entry starts after PC zero trigger `Bytecode2TCCode.getLineOfPC` with index `-1`. Removing the attribute is necessary to collect later structural evidence, but its 4.302% TCZ-byte and 7.277% class-payload effects must not be credited to optimization. The untouched ordinary baseline remains the primary corpus.
  Date: 2026-08-08.

- Decision: Stop safe-shrink rule expansion after two narrow converter-compatibility observations.
  Rationale: the API snapshot passed for all modules, but `misc` success moved from an inherited `Properties.put` owner rejection to a `System.getProperty` replacement-owner rejection after one exact code pin. Continuing to pin until conversion passed would no longer be a trustworthy reachability estimate.
  Date: 2026-08-08.

- Decision: Recommend bounded field optimization near J2TC rather than whole-program HIR, ProGuard integration, or tree shaking.
  Rationale: the compatible field family reduces aggregate TC code slots by 3.495%; its module-local form achieves 3.397%, leaving only a 0.097 percentage-point whole-runtime advantage. Field propagation, marking, and removal explain the signal, while enum unboxing is negligible, safe shrinking is weak/partial, and full ProGuard variants are J2TC-incompatible.
  Date: 2026-08-08.

```text

baseline TCZ analysis fails
ProGuard engine cannot be resolved or launched
experiment output isolation is broken
machine-readable evidence is corrupt
```

is rejected by ProGuard

## Risks and Open Questions

### Runtime libraries are not applications

The four runtime modules are strong autonomous build artifacts but are libraries, not a closed-world application.

Their public surface and dynamic usage may constrain shrinking and some whole-program transformations.

If this materially limits interpretation, use the existing smoke application as the bounded secondary corpus or conclude that a real application corpus is required.

Do not fetch unrelated external applications automatically.

### J2TC has TotalCross-specific conventions

The converter and deployer handle class replacement, `4D` classes, dynamic class loading, native/runtime conventions, and other behavior that a generic Java optimizer does not intrinsically know.

Optimize-only experiments should preserve names and metadata to minimize this risk.

Shrinking requires explicit pinning and must remain a separate milestone.

### Java metadata can affect conversion

Do not remove attributes simply to obtain a smaller JAR.

Preserve metadata during the primary experiment so TCZ differences primarily represent code transformations rather than accidental changes in converter inputs.

### Compression can mislead

A smaller compressed TCZ may result from more compressible bytes rather than less executable work.

Always report uncompressed chunk payload and structural TC metrics alongside final file size.

### TC instruction count is not runtime time

Reducing TCCode slots is a useful structural signal for an interpreter but does not prove a proportional runtime improvement.

Virtual dispatch, allocations, helper calls, GC, memory behavior, and code locality may dominate.

Keep performance conclusions separate unless actual execution is measured.

### ProGuard behavior is not a TotalCross specification

ProGuard is used here as an optimization oracle.

A transformation that ProGuard performs is evidence that an opportunity exists; it is not automatically the correct implementation or semantic contract for TotalCross.

## Outcomes & Retrospective

The ordinary corpus at revision `aa6b2ff3ded73a845848c014ee54fae9bcfc7a77`
contains four runtime JARs totaling 2,932,789 bytes and four TCZs totaling
1,577,089 bytes. The TCZ analyzer recovered 1,125 TC classes, 10,703 TC
methods, 229,556 TC code slots, and 1,306,648 bytes of actual decompressed TC
class payload. Reanalysis was deterministic, and the final experiment run
verified that all eight ordinary artifact hashes still matched this baseline.

ProGuard 7.9.1 was resolved in an isolated Gradle configuration. Full
conservative module-local optimization, one-pass whole-runtime optimization,
and three-pass whole-runtime optimization all completed ProGuard processing but
were rejected by J2TC. The failures were reproducible across replacement-class
constructor or method signatures, generated method names, device-API owner
checks, and operand-stack assumptions. An earlier failure also proved that
valid optimized line tables may begin after PC zero while J2TC assumes an entry
at or before every translated PC.

The compatibility diagnostic removes only `LineNumberTable` after ProGuard.
The corresponding no-line baseline proves that this adjustment alone reduces
TCZ bytes by 4.302% and TC class payload by 7.277%, while changing neither TC
method count nor TC code slots. All optimization conclusions use that
normalized comparison, so debug metadata is not misattributed to compiler
benefit.

The complete field group is the only successful moderate signal across all four
modules. It reduces aggregate TC code slots by 3.495%, TC field accesses by
4.775%, virtual calls by 2.635%, normal calls by 1.803%, allocations by 0.820%,
TC methods by 0.729%, TC class payload by 2.865%, and final TCZ bytes by 1.335%.
The module-local field run reaches 3.397% fewer TC code slots and 2.792% less TC
class payload. Whole-runtime context therefore adds only 0.097 percentage point
of code-slot reduction and 0.074 point of class-payload reduction.

Field propagation independently reduces TC code slots by 1.435%, field marking
by 1.139%, and field removal by 0.501%; their combination has a useful
interaction. Field generalization and specialization do not change TC code
slots. Enum unboxing changes slots by only 0.007%. Local code/data-flow
optimization succeeds only for `lang`, where it reduces slots by 2.934%, and is
rejected for the other three modules. The method group succeeds only for `ui`
and increases its slots by 5.428%, so it is not positive evidence for an
interprocedural HIR.

The conservative safe-shrink configuration preserves every public/protected API
snapshot entry after keep rules stop optimizing the kept API. ProGuard reports
eight removed classes and 473 removed-member lines in 86 retained classes.
`lang`, `util`, and `ui` convert, but `misc` remains incompatible after the
narrow `DriverManager` pin exposes a second replacement-owner failure in
`Settings`. The accepted three-module aggregate is weak and shrinking worsens
TC code slots by 2.604% relative to compatible field-only optimization on the
same coverage. Safe shrinking is therefore unresolved and does not support
tree shaking as the next investment.

No semantic runtime-speed percentage is claimed. Successful variants passed
ProGuard, deterministic module reconstruction, J2TC conversion, TCZ structural
parsing, and API validation where applicable. The corpus is the shipping SDK
runtime rather than a representative closed-world application set, and the
no-line compatibility path loses device stack-trace detail.

The measured opportunity is predominantly module-local and does not justify a
new Java-aware whole-program HIR. The next compiler investment should be a
bounded pre-J2TC/J2TC field-propagation, field-marking, and field-removal effort
that preserves TotalCross `4D`, native, reflection, and device-API conventions,
with the ProGuard field variants retained only as an oracle. Before broadening
that work into a general Java optimizer, obtain application-level evidence.
Production ProGuard integration and reachability/tree shaking are not supported
by this experiment. TCIR/JIT/AOT remains a separate runtime-performance path;
this structural experiment neither measures nor prioritizes it over the bounded
field opportunity.
