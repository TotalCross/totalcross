# TotalCross 7.3.0

**Release date:** October 28, 2026  
**Commits since 7.2.2:** 614

TotalCross 7.3.0 is a major modernization and stabilization release. It expands the supported Java toolchain through Java 17, introduces density-independent logical UI coordinates, substantially rebuilds the image and rendering pipeline, modernizes the Windows desktop runtime, updates Android and iOS for current store requirements, and strengthens deployment, runtime configuration, artifact validation, and release infrastructure.

The release also contains substantial compiler and VM research. Experimental TCIR, JIT, and AOT work is documented separately and remains disabled by default.

---

## Migration Summary

Before upgrading from 7.2.2, review the following areas.

1. **Review code that manually converts DP or logical values to physical pixels.**  
   UI layout now uses logical coordinates by default. `UnitsConverter.toPixels()` is retained for compatibility but no longer performs the historical density conversion.

2. **Android now requires API 24 or later.**  
   Android 6.0 / API 23 devices can no longer install applications generated with TotalCross 7.3.0.

3. **Android applications should review manifest permissions.**  
   Sensitive optional permissions are no longer broadly included in every generated application. Use `/android_permission <fully.qualified.permission>` or the retained legacy flags when those capabilities are actually required.

4. **Android now targets API 36 / Android 16.**  
   This aligns mobile application builds with the Google Play target API requirement in force since August 31, 2026. See the [Google Play target API requirements](https://support.google.com/googleplay/android-developer/answer/11926878).

5. **iOS applications now use an iOS 13 deployment target.**  
   The build pipeline uses Xcode 26 and the iOS 26 SDK. These match the current App Store Connect requirements for uploads: iOS 13 or later as the minimum deployment target, and Xcode 26/iOS 26 SDK or later. See [Apple's current submission requirements](https://developer.apple.com/news/upcoming-requirements/).

6. **Custom tooling that expects the monolithic `TCBase.tcz` should be reviewed.**  
   The device base library is split into smaller modules including `tc.base.lang`, `tc.base.util`, and `tc.base.misc`.

Applications that depend on the old pixel-based root layout can explicitly select `LayoutUnit.PIXEL`.

For image controls, prefer retaining the original source image and letting `ImageControl` and the runtime resolve the appropriate destination scale instead of manually pre-scaling assets for the current display density.

## Highlights

### Developer Action Required

#### Logical coordinates are now the default UI model

UI layout is now expressed in logical coordinates independently from the physical pixel density of the rendering surface.

The change addresses long-standing cases where density-dependent layout and off-screen rendering could disagree, including text and graphics rendered to `Image` surfaces.

Fonts, primitives, images, transforms, clipping, hit testing, and input coordinates now resolve through per-surface `contentScale` and `fontScale`.

Applications that manually multiply positions, dimensions, or image sizes by screen density should review that code.

#### Android support baseline changes

TotalCross 7.3.0 raises the Android minimum from API 23 to **API 24** and targets **API 36 / Android 16**.

The API 36 target is directly relevant to Google Play compatibility. The API 24 minimum is a TotalCross support-policy decision rather than a Play Store requirement.

#### Android permissions are more explicit

Applications can now declare additional manifest permissions with:

```text
/android_permission <fully.qualified.permission>
```

The existing `/android_manage_external_storage` and `/android_request_install_packages` options remain available.

`READ_MEDIA_IMAGES`, `READ_MEDIA_VIDEO`, `MANAGE_EXTERNAL_STORAGE`, and `REQUEST_INSTALL_PACKAGES` are no longer unconditionally included in the default Android application template.

This reduces the chance that an application inherits sensitive permissions it does not use and makes TotalCross applications easier to align with current Google Play storage, media, and package-installation policies. Applications that explicitly request restricted permissions remain responsible for satisfying the corresponding Play Console policy and declaration requirements.

#### iOS support baseline changes

The configured iOS deployment target is now **iOS 13**.

macOS/iOS CI uses **Xcode 26 and the iOS 26 SDK**, matching the current App Store Connect build-tool requirements. Applications that need devices older than iOS 13 should review their support strategy before upgrading.

---

### Major New Capabilities

#### Modern Java compiler output through Java 17

TotalCross can now consume mainstream `javac` output through Java 17 without requiring Retrolambda for ordinary Java 8 lambda use.

The supported compiler patterns include:

- Java 8 lambdas and method references;
- captured lambdas and common `LambdaMetafactory` / `altMetafactory` output;
- Java 9+ `StringConcatFactory` concatenation;
- Java 11 and Java 17 class files;
- records, including normal `equals`, `hashCode`, and `toString` behavior;
- default and static interface methods;
- nestmate, module, and sealed-class metadata.

This should be read as **support for mainstream compiler output through Java 17**, not as a claim that the complete Java 17 standard library or module runtime is implemented.

`CONSTANT_Dynamic` structures can be parsed, while dynamic constants loaded through `ldc` remain unsupported.

#### Native macOS deployment

`tc.Deploy` can now produce native macOS application output, including the application TCZs, Launcher, and native VM.

The packaged SDK validation now exercises macOS deployment alongside Windows, Android, iOS, Linux, and Linux ARM targets.

#### Native speech-to-text on iOS

The existing `Sound.toText(String)` API now has an iOS implementation using Apple's Speech framework and AVAudioEngine.

The public Java API remains unchanged, allowing applications already using `Sound.toText()` on Android to use the same call on iOS.

The iOS template includes the microphone and speech-recognition purpose strings required by the platform when these APIs are used.

#### IDE-independent preview foundation

Launcher presentation is abstracted behind reusable preview surfaces, and a headless preview runner is available as the basis for IDE integrations.

The architecture is intentionally IDE-independent so editors can reuse the same preview runtime instead of implementing separate rendering paths.

### Major Runtime Improvements

#### Rebuilt image and rendering pipeline

The image subsystem is substantially redesigned around lazy decoding, deferred transformations, native backing, destination-aware resolution, bounded raster caching, and explicit preparation.

Encoded PNG/JPEG data can remain authoritative until pixels are required. Compatible operations such as scaling, cropping, rotation, frame selection, layout, and color transformations can remain deferred rather than eagerly allocating full-size intermediate rasters.

On deployed Skia runtimes, `Image` can retain native backing without requiring a persistent Java `int[]` proportional to the decoded image.

`Image.getJpegBestFit()` and `Image.getJpegScaled()` participate in this lazy pipeline while preserving their public dimensions and scaling semantics.

Persistent UI consumers can retain an appropriate final raster, reducing repeated reconstruction of the same transformed image.

#### Rendering benchmark

A production-candidate benchmark on **macOS ARM64**, using a 540×960 logical surface rendered at 1080×1920 with scale 2, measured:

- warm `paintTree`: **5.509 ms**;
- cumulative image paint: **4.984 ms**;
- 18 final-raster cache hits and 0 misses;
- no generic geometry materialization or smooth resampling in the measured warm frame.

For repeated scrolling:

- cold forward p50/p95/max: **70.456 / 73.900 / 98.178 ms**;
- warm reverse p50/p95/max: **16.348 / 16.743 / 30.483 ms**;
- warm forward p50/p95/max: **16.313 / 16.627 / 47.995 ms**.

No interval exceeded 100 ms across **9,720 measured frame intervals**.

These measurements apply to this specific macOS workload. Windows passed build/integration validation, but an equivalent dedicated Windows performance benchmark was not executed.

#### Compact native image storage

Eligible immutable images can use compact Skia backing formats such as RGB565, GRAY8, or premultiplied ARGB4444, with RGBA8888 as the standard fallback.

Focused 8×6 fixtures measured:

- RGBA8888: 192 bytes;
- RGB565: 96 bytes;
- GRAY8: 48 bytes;
- ARGB4444: 96 bytes.

These values describe the backing for the measured fixture and are not whole-process memory measurements.

Images are promoted to standard writable storage before incompatible mutations.

#### Explicit asynchronous preparation

`ScrollContainer.prepareForDisplay(Runnable callback)` can explicitly prepare eligible visible JPEG and supported single-frame PNG images before the normal drawing path needs them.

Preparation is **not automatic**. Ordinary scrolling does not implicitly start background preparation, and multi-frame PNG remains synchronous.

## Changes for SDK Users

### Java and Runtime

#### Standard streams and monotonic timing

The deployed runtime now provides independent `System.out` and `System.err` streams while preserving `Vm.debug` / `DebugConsole` compatibility.

`System.nanoTime()` is backed by a monotonic native clock and does not change the historical `Vm.getTimeStamp()` contract.

#### Semaphore compatibility

A native-backed, non-fair compatibility subset of `java.util.concurrent.Semaphore` is available.

The initial supported operations cover the common single-permit forms:

- construction with an initial permit count;
- `acquire()`;
- `acquireUninterruptibly()`;
- `tryAcquire()`;
- `release()`.

Timed, multi-permit, and fairness APIs are outside this initial compatibility surface.

#### Earlier deployed-API validation

SDK validation now checks direct `java.*` / `javax.*` calls against the same device model used by the converter and built-in TCZ deployment.

This moves failures earlier when code compiles against the host JDK but calls a method or constructor not implemented by the deployed TotalCross runtime.

A generated deployed-Java API manifest provides a queryable view derived from the same source of truth.

---

### UI, Layout, and Rendering

#### Logical UI scaling

`MainWindow` defaults to logical layout.

The old encoded DP marker model is deprecated. `UnitsConverter.toPixels()` remains as a compatibility API but no longer performs the previous global-density conversion.

Applications that intentionally depend on the legacy pixel layout can opt into root `LayoutUnit.PIXEL`.

#### Safe-area behavior

Android and iOS presentation automatically constrain the application surface to the usable safe region.

The 7.3.0 behavior remains automatic confinement rather than a new edge-to-edge application model.

#### Unified Image implementation

The separate deployed `Image4D` implementation is removed.

`Image` is now the common source for JavaSE and deployed semantics, with platform-specific native backing and deployment bridges isolated behind explicit boundaries.

#### Typed runtime image policies

Runtime configuration can select image behavior by platform, runtime family, graphics backend, and architecture.

Image policy includes:

- storage profile;
- target-color conversion;
- physical variant caching;
- scroll raster reuse;
- preparation worker selection.

Windows desktop defaults to compact storage, target-color conversion, physical variants, and the semaphore preparation worker.

`scrollRasterReuse` remains disabled by default, as does automatic display preparation.

Other platforms retain their conservative defaults unless explicitly configured.

## Windows

### SDL2 + Skia is the default desktop path

Windows desktop now uses SDL2 windowing with Skia software-raster presentation by default.

The previous native/legacy software path remains available as a fallback, and WinCE remains on its legacy path.

The SDL desktop path owns normal text, keyboard, modifier, mouse/touch, lifecycle, and Windows hotkey event delivery.

Window startup behavior for dimensions, `/scr`, fullscreen, maximized, resizable, positioning, and environment overrides is centralized.

### TrueType fonts in the normal Skia runtime

Windows Skia loads normal TTF resources directly, with deterministic lookup, dynamic typeface storage, safe fallback, invalid-font rejection, and proper bold measurement/rendering.

Generated legacy PalmFont/font-TCZ assets remain relevant primarily for the Java simulator and legacy renderer rather than the normal Windows Skia runtime.

### Windows image defaults

Windows desktop now automatically enables the image policies that were previously opt-in:

- compact storage;
- target-color conversion;
- physical variant caching;
- semaphore-backed preparation worker.

The runtime still keeps scroll-raster reuse and automatic preparation disabled by default.

No Windows performance percentage is claimed from this default change because the dedicated Windows benchmark was not executed.

### Better deployed application icons

The Win32 deployer keeps the existing 32×32×8-bit Launcher resource format, but improves image conversion quality.

PNG/GIF sources now use:

- premultiplied-alpha processing;
- progressive bicubic downscaling;
- an adaptive per-image 256-color palette;
- Floyd–Steinberg error diffusion;
- source-alpha-derived transparency when available.

This improves small-icon quality without changing `Launcher.exe`, expanding the icon resource format, or adding a runtime dependency.

### Static MSVC runtime

Windows native builds link the MSVC runtime statically. `vcruntime140.dll` is therefore no longer distributed beside generated applications.

## Android

### Google Play compatibility

Android applications now target **Android 16 / API 36**.

Google Play requires new mobile applications and application updates submitted since August 31, 2026 to target API 36 or later. TotalCross 7.3.0 therefore brings the normal Android application target in line with the current store requirement.

The minimum API level is separately raised to **24**. That minimum is a TotalCross compatibility decision, not a Google Play mandate.

### Permissions and privacy

Android permission handling is redesigned around explicit manifest declarations and authorization when the corresponding operation is used.

A common permission coordinator serializes/coalesces requests, handles special-access flows, and applies bounded waits.

Changes include:

- explicit `/android_permission` declarations;
- speech authorization on demand;
- package-install authorization on demand;
- camera/gallery access through scoped content URIs;
- Android 14 partial media-grant handling;
- bounded permission recovery after filesystem `EACCES` / `EPERM`.

Applications that choose restricted permissions such as broad storage access or package installation remain responsible for their own Google Play eligibility and declaration requirements.

### Camera and media

External camera/gallery operations use content URIs and URI streams instead of depending on unrestricted external file paths.

Capture state can survive activity recreation, CameraX recording receives additional finalization/concurrency protection, and output destinations are validated before use.

### Native document viewers

`Vm.exec("viewer", path, ...)` can dispatch local DOCX, XLSX, CSV, PPTX, PDF, and other MIME-supported documents to installed Android applications.

Existing internal handling for images, HTML/TXT/XML, URLs, and related content remains intact.

### Modern system Back handling

System Back events now flow through the Android activity callback path and into the TotalCross event thread, with keyboard dismissal and legacy-event deduplication.

### Location updates

The fused-location implementation uses the modern builder API and requests one-second updates with zero minimum distance.

### Bluetooth stability

Bluetooth operations use bounded request lifecycles with cancellation and monotonic deadlines.

Connection, discovery, I/O, server, and cleanup paths are hardened so failed operations and VM shutdown do not indefinitely block the Android UI thread.

The native SPP boundary also rejects null, empty, or oversized client address strings before conversion.

### Offline Android tools

`tc.Deploy -download-tools` can prepare the versioned Android deployment tools needed for later offline deployment.

## iOS

### App Store compatibility

The iOS project is configured with an **iOS 13 deployment target**, and CI uses **Xcode 26 with the iOS 26 SDK**.

Apple requires App Store Connect uploads since April 28, 2026 to be built with Xcode 26 or later using the iOS 26 SDK or later, and since September 9, 2026 requires iOS applications to target iOS 13 or later.

### Speech recognition and privacy

`Sound.toText()` is implemented natively on iOS.

The generated application supplies the microphone and speech-recognition purpose strings used by the Apple permission system, and the native bridge handles authorization, recording, completion, cancellation, silence timeout, interruption, and error paths while preserving the existing Java return contract.

### Safer IPA re-signing

`tccodesign.sh` now verifies that the executable identity and Mach-O UUID/architecture set in the input IPA match the expected archive before signing.

The process also uses isolated temporary workspaces, validates required inputs, propagates critical failures, provides clearer CLI help, and supports grouped output using `--group`.

## Relevant Bug Fixes

### Converter float parameter mapping

A long-standing converter bug treated JVM `float` parameters as if they consumed two local-variable slots.

A JVM `float` consumes one slot, even though TotalCross stores it in the same internal `reg64` family used for `long` and `double`.

The previous behavior could therefore shift parameters following a `float` and generate incorrect converted code.

The old workaround requiring a float parameter to be last is no longer necessary.

### Programmatically generated images on Android/Skia

Fixed generated or programmatically drawn images becoming blank when Java image state and the native Skia surface disagreed about the authoritative pixel contents.

Rendering into an image now updates the correct backing and invalidates stale presentation state.

### JPEG scaling factory correctness

`Image.getJpegBestFit()` and `Image.getJpegScaled()` now preserve consistent dimensions, scaling metadata, and adaptive decode behavior, including odd dimensions and the supported JPEG denominator tiers.

### `Integer.toHexString(int)`

The implementation now matches JDK semantics across the full 32-bit value:

- lowercase output;
- no fixed four-character padding;
- no truncation to the low 16 bits;
- normal two's-complement representation for negative values.

### iOS certificate date

`Settings.iosCertDate` is populated correctly again.

### Method references

Converter support now handles method references used through generic functional interfaces in cases that previously failed compilation.

## Native Dependencies

Native dependency acquisition and packaging are further consolidated around the pinned `totalcross-depot-tools` manifest.

Important technology changes include:

- JPEG decoding moved to **libjpeg-turbo**;
- legacy MiniZip usage migrated toward **minizip-ng**;
- axTLS and QR code sources moved out of the main repository into managed dependency artifacts.

Depot artifact suffixes such as `-r2` and `-r3` represent TotalCross package revisions and do not by themselves indicate an upstream library upgrade.

### libjpeg-turbo measurement

During the JPEG backend migration, a focused i.MX6ULL workload using a 2500×1095 JPEG reported approximately:

- **50% faster** full-size loading;
- **20% faster** `Image.getJpegBestFit()` loading at approximately 1250×548.

These figures apply to that hardware and workload rather than all TotalCross platforms.

## Internal Project Changes

### Generated native bridges

Native bridge declarations and registrations are derived from the Java classes that survive device deployment rather than depending primarily on manually synchronized native inventories.

Generation checks symbol collisions, compatibility registrations, and concrete native definitions before native platform compilation.

### Artifact provenance and compatibility

SDK JARs, converter-produced TCZs, VM binaries, and Launchers embed deterministic build identity/source provenance.

Separate compatibility epochs describe TCZ format, converter ABI, and runtime ABI compatibility independently from exact source identity.

Packaging validates that downloaded artifacts belong to a coherent build instead of silently combining unrelated outputs.

### CI and build pipeline

Pull-request CI can skip unnecessary native work for documentation-only or SDK-only changes while conservatively falling back to the full matrix for ambiguous changes.

Native dependency preparation and bridge generation run in parallel, and Android CI removes redundant compilation/clean work while using Gradle-aware caching.

### Maven Central release support

The release workflow can construct and validate a Maven Central-compatible `com.totalcross:totalcross-sdk` bundle with:

- main SDK JAR;
- sources JAR;
- Javadoc JAR;
- Maven POM;
- PGP signatures;
- MD5/SHA-1/SHA-256/SHA-512 checksums.

Publication to Maven Central and the legacy `maven.totalcross.com` repository remains explicit opt-in behavior. A normal tag push does not automatically publish to either Maven repository.

### Versioned release notes

Human-oriented release notes are now stored under `docs/releases/<version>.md` and are the mandatory source used to create GitHub Releases.

`CHANGELOG.md` remains the concise historical ledger based on Keep a Changelog.

The release workflow fails when the matching release-note file is absent, empty, or does not identify the expected TotalCross version.

## R&D and Experimental Work

### TCIR, JIT, AOT, and compiler research

A substantial compiler/VM research track is included in the repository without changing the default production execution path.

The work includes:

- a typed, verified TotalCross intermediate representation (TCIR);
- an independent TCIR reference interpreter;
- an experimental SLJIT baseline JIT;
- an experimental portable-C AOT backend;
- converter/backend differential tests;
- opt-in semantic metadata through TCM;
- architecture and compatibility documentation.

TCZ and the legacy interpreter remain the production compatibility authority.

The research concluded that TCIR is viable as a backend/runtime IR after TotalCross bytecode lowering, but that this stage is too late to reconstruct all Java-level information required for R8-style optimization.

The current evidence does not justify enabling the experimental JIT/AOT paths, a broad Java-aware HIR, or a ProGuard pre-pass in production.

The strongest identified next compiler optimization direction is a bounded field propagation/marking/removal pass before or inside J2TC.

No production performance improvement from the experimental JIT or AOT paths is claimed in 7.3.0.
